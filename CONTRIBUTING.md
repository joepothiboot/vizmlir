# Contributing to VizMLIR 🤝

Thanks for taking the time to improve VizMLIR. Small, focused changes are welcome, especially improvements to MLIR parsing, graph rendering, and the browser workflow.

## 🧰 Before you start

1. Install Node.js 20 or newer, Rust, Cargo, and the `wasm32-unknown-unknown` Rust target.
2. Install dependencies with `npm ci`.
3. Start the app with `npm run dev` and open the local URL printed by Vite.

## 🗺️ Project layout

Source is grouped by domain, not by file type. Each folder under `src/` has an `index.js` barrel that lists what other folders may import, and a README with the details: [`ir`](src/ir/README.md), [`trace`](src/trace/README.md), [`gpu`](src/gpu/README.md), [`render`](src/render/README.md), [`session`](src/session/README.md) and [`app`](src/app/README.md).

| Path | Belongs here | Does not belong here |
| --- | --- | --- |
| `src/main.js` | The entry (`index.html` loads it) and the wiring of the UI and application state. | Logic another module could own. |
| `src/ir/` | The JavaScript side of the Rust module: ABI constants (`abi.js`), the `MlirEngine` bridge, memory views, and snapshot copy and diff (`diff.js`). | Anything that reads IR text; the Rust source (`wasm/src/`). |
| `src/trace/` | Pass-trace parsing, timing, op counts, buffer liveness, symbol history and line diffs: analyses of IR text and pass events. | DOM code, rendering, `wasm` bindings. |
| `src/gpu/` | The GPU model, scratchpad (local memory) analysis, memory-access verdicts, the affine proof engine, kernel flow and Triton layouts. DOM-free analysis. | Drawing code; it belongs in `render/`. |
| `src/render/` | Everything drawn: the graph canvas, the GPU view, the Local memory view and the 3D scene. | Analysis; put it in `gpu/` or `trace/` and import it. |
| `src/session/` | Autosave and named sessions, `.json` share files, Markdown/JSON/patch export, and live-reload file watching. | Analysis or drawing. |
| `src/app/` | The shell: command palette, inspector drawer, pass slider, splitters, editor highlighting and the buffers tab view. | Domain analysis. |
| `src/anatomy.js`, `bench.js`, `samples.js` | Line explainer, benchmark import and the built-in sample list. They stay at the root until they have company: a folder needs three files. | |
| `wasm/src/` | The MLIR lexer, parser, arena, and exported ABI. A separate Rust crate (`wasm/Cargo.toml`). | JavaScript. |
| `public/mlir_core.wasm` | Generated by the WASM build; never edit it by hand. | |
| `public/samples/` | Built-in samples, generated from `samples/input/` by `MLIR_OPT=/path/to/mlir-opt samples/generate.sh`. Regenerate rather than hand-edit, and register new ones in `src/samples.js`. | |

**Import direction.** `ir` and `session` import from no other folder. `trace` imports `ir`. `gpu` imports `trace`. `render` imports `gpu`, `trace` and `ir`. `app` imports `trace`. Only `main.js` imports from everything. Analysis folders (`ir`, `trace`, `gpu`) must not touch the DOM and must never import `render` or `app`.

**Imports.** Across folders, import through the barrel (`../gpu/index.js`). Inside a folder, import files relatively (`./access.js`). Tests may import the file under test directly. When another folder needs a new symbol, add it to the barrel in the same change.

## ✍️ Making changes

- Keep changes focused and preserve the existing browser-only architecture.
- When changing `wasm/src/abi.rs`, update the matching declarations in `src/ir/abi.js`.
- When changing parser output, check both valid input and malformed MLIR in the app.
- Do not commit build output from `dist/`, `wasm/target/`, or generated WASM unless a release process specifically requires it.

## 🔎 Blame

The `src/` restructure moved files with `git mv` in commits that change no content. Tell git to look past them so `git blame` points at the real author of each line:

```bash
git config blame.ignoreRevsFile .git-blame-ignore-revs
```

GitHub's blame view reads `.git-blame-ignore-revs` automatically. Add the hash of any future move-only commit to that file.

## ✅ Checks

Run the full production build before opening a pull request:

```bash
npm run build
```

For Rust-only changes, these checks are also useful:

```bash
cargo fmt --manifest-path wasm/Cargo.toml -- --check
cargo check --manifest-path wasm/Cargo.toml --target wasm32-unknown-unknown
```

## 🚀 Deployment

Pushes to `main` run `.github/workflows/deploy-pages.yml`, which builds `dist/` and publishes it to https://joepothiboot.github.io/vizmlir/. The repository's Pages source must be **GitHub Actions** (Settings → Pages → Build and deployment).

> ⚠️ If it is set to "Deploy from a branch", GitHub serves the raw repository instead: the page loads `./src/main.js` unbundled, it throws on `import.meta.env.BASE_URL`, and no JavaScript control works (only native ones such as Open…). The workflow's last step checks for this and fails.

To check the setting and what the live site serves:

```bash
gh api repos/joepothiboot/vizmlir/pages --jq .build_type   # expect "workflow"
curl -s https://joepothiboot.github.io/vizmlir/ | grep '<script'   # expect /vizmlir/assets/index-*.js
```

When a bug is reported against the live site but not reproducible with `npm run dev`, reproduce it on the live URL first; it may be a deployment problem rather than a code one.

In a pull request, describe what changed, how you tested it, and include a small MLIR example when the behavior is parser- or rendering-related.
