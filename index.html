                A visual guide to GPU compilers
                  VizMLIR · a visual guide

                  How does your code end up on a GPU?

                  Between the program you write and the instructions a GPU runs sits a compiler that rewrites your code dozens of times. Each rewrite decides something that matters: how the work is split among thousands of threads, where the data is kept, and whether it is read in a way the hardware is good at.

                  This guide teaches those ideas with real compiler output from MLIR, the compiler framework behind many modern GPU and machine learning compilers. Every idea comes with a picture in VizMLIR you can poke at, and a short question to check yourself.

                  Where this fits in a CS course

                  Computer architecture
                  How a GPU runs threads in lockstep (SIMT), its memory hierarchy, and why the order of memory accesses changes speed.
                  Compilers
                  Intermediate representations, SSA form, passes, and lowering a program from high-level operations down to assembly.
                  Parallel programming
                  Mapping loops onto a grid of threads, thread indexing, and the classic transpose and tiled matrix multiply.

                  What you need

                  Loops, arrays, and a rough idea that memory is a long row of numbered bytes. No compiler, GPU, or CUDA experience needed.

                  The course

                  A promise and a limit. VizMLIR only reads code. It never runs it, and nothing leaves your browser. That also means it shows the patterns that make a GPU fast or slow, not exact timings; a profiler measures those.

                  Start here

                  Lesson 1 · Architecture

                  How a GPU runs code

                  You'll learn
                  • what threads, blocks, and the grid are;
                  • why threads move in groups of 32 called warps;
                  • how each thread finds the piece of data it owns.

                  A CPU has a few powerful cores that each follow their own instructions. A GPU has thousands of simpler ones built to run the same instructions on different data. Instead of one loop that visits every cell of a table, a GPU program says what to do with one cell, and the hardware runs that piece of code once per cell, all at the same time. That piece of code is a kernel.

                  Threads
                  Each running copy of the kernel is a thread. Think of thousands of people each handed one cell of a huge spreadsheet.
                  Blocks and the grid
                  Threads come in teams called blocks, and all the blocks together make the grid. Blocks never wait for each other, so the GPU can spread them over its cores in any order.
                  Warps
                  Inside a block, the hardware runs threads in groups of 32 called warps, executing one instruction for all 32 at once. This is called SIMT: single instruction, multiple threads. When one thread in a warp reads memory, all 32 read at the same moment.

                  Which thread am I?

                  Every thread knows its position: its block number and its thread number inside the block. The kernel turns those into "my cell". In the transpose sample, that looks like: 

                  %x0 = arith.muli %bx, %c32 : index   // block x × 32
%x  = arith.addi %x0, %tx : index    // + thread x
%y0 = arith.muli %by, %c32 : index
%y  = arith.addi %y0, %ty : index

                  With blocks of 32 × 32 threads, thread (tx, ty) of block (bx, by) owns cell (bx·32 + tx, by·32 + ty). The first warp is the 32 threads with ty = 0 and tx = 0 to 31.

                  Try it. In the transpose sample, look at the GPU view: a grid of squares, one per block. The highlighted block is opened below it, 32 threads to a row; each row is one warp. Hover a square for its number.
                  Check yourself: the tiled matmul sample uses blocks of 16 × 16 threads. How many warps is each block?

                  16 × 16 = 256 threads, and 256 / 32 = 8 warps. Open "Tiled matmul on the GPU" from Samples and count the rows in the opened block.

                  Lesson 2 · Architecture

                  Memory and access patterns

                  You'll learn
                  • the three kinds of GPU memory and why they differ;
                  • what makes a warp's access coalesced or strided;
                  • what a shared-memory bank conflict is, and one fix.

                  Near and far memory

                  Global
                  The big warehouse every thread can reach. Large, but far away: each trip is slow, so the GPU fetches it in chunks of 32 bytes called sectors.
                  Shared
                  A small shelf inside each block, quick to reach and shared by that team only. Programs copy a tile of data here once, then read it many times.
                  Private
                  Registers that belong to a single thread.

                  Coalesced or strided

                  Because a warp's 32 threads read at the same moment, what matters is where their 32 addresses land.

                  coalesced
                  Neighboring threads read neighboring items, like taking books side by side from one shelf. 32 floats of 4 bytes are 128 bytes: four sectors, the least possible.
                  strided
                  Threads read items far apart, like 32 people each walking to a different aisle. Each thread pulls in its own 32-byte sector to use 4 bytes of it: 32 sectors instead of four, eight times the traffic.
                  misaligned
                  Neighbors read neighbors, but the row starts partway into a sector, so it spills into one more: five sectors instead of four. Cheaper than strided, and fixed by starting on a multiple of 32 bytes.
                  broadcast
                  Every thread reads the same item. The GPU fetches it once and hands out copies.

                  Bank conflicts

                  Shared memory is split into 32 banks, like 32 service counters; consecutive 4-byte words go to consecutive counters, wrapping around. If several threads of a warp need different words from the same bank, they queue.

                  bank conflict
                  "32-way" means all 32 threads wait in one line: the access takes 32 turns instead of one.
                  no conflicts
                  Everyone is served at their own counter at once.

                  Reading the GPU view

                  For every launch (a place the program starts work on the GPU), the view shows the grid and one opened block, every array sorted into global, shared, and private memory, and every read and write with a verdict. Click an access to see its 32 threads as colored squares (same color, same sector or bank) and to mark its line in the code.

                  The answer card, in the inspector's Line tab, sums up the picked access: its verdict, one sentence on what it costs, and a bar for how much of the memory traffic is useful. The line above the GPU view repeats the verdict in short; click it to open the card. Next to the verdict:

                  ✓ all 32,768 warps
                  Proven. The address is a linear function of the thread ids, block ids and loop counters, so VizMLIR checked every warp of the launch and every trip through the loops, not just the first warp.
                  varies across warps
                  Some warps or loop trips do better than others, usually because the address drifts out of line with the 32-byte sectors. The card says how often each case happens.
                  warp 0 only
                  The address uses something VizMLIR can't reason about for every warp (a division, say), so only the first warp was checked.

                  Compiler on the card swaps the sentence for the math: the element offset as a formula of the ids, and how far apart neighboring threads land. With a pass trace open, Across passes shows the same access at every pass, so you can see which pass made it better or worse. In the 3D view, the memory plate next to the opened block holds the elements the first warp touches, with a line from each thread to its element: a row of threads fanning into one column is a strided access. Elements (e) shows the same buffer flat, from above.

                  For Triton kernels, the layout of a tensor decides which elements each thread holds, and so what a warp reads together. Who holds which element draws it: one square per element, colored by warp and numbered by lane. Open the Triton sample and step from the first pass to the second to watch the coalesce pass turn a row of lanes into columns of 4-wide vectors.

                  Try it. In the transpose sample, compare the three kernels' accesses: the naive one's write, the 32 × 32 tile's read, and the padded 32 × 33 tile.
                  Check yourself: the naive transpose reads in[%y, %x] and writes out[%x, %y]. Across the first warp only %x changes. Which one is strided?

                  The write. In in[%y, %x], %x is the column, so neighbors are 4 bytes apart: coalesced. In out[%x, %y], %x is the row, so neighbors are a whole row (1024 × 4 bytes) apart: 32 sectors for 128 useful bytes.

                  Check yourself: why does padding a 32 × 32 shared tile to 32 × 33 remove the bank conflict when threads read down a column?

                  Thread t reads word t·32 + c, whose bank is (t·32 + c) mod 32 = c: the same bank for all 32 threads. With rows of 33 words, the bank is (t·33 + c) mod 32 = (t + c) mod 32, which is different for every thread.

                  Lesson 3 · Compilers

                  Reading MLIR

                  You'll learn
                  • what an intermediate representation (IR) is;
                  • the parts of a line: value, operation, operands, type;
                  • what SSA form and dialects are.

                  Compilers don't rewrite your source text directly. They first translate it into an intermediate representation: a simpler, regular language that is easy to analyze and transform. MLIR is a framework for building such IRs, and the code in VizMLIR's left panel is MLIR.

                  Anatomy of a line

                  %4 = memref.load %arg0[%3, %1] : memref<1024x1024xf32>

                  %4 =
                  The value this line produces. Later lines use it.
                  memref.load
                  The operation: load (read one item) from the memref dialect, a family of operations on arrays in memory.
                  %arg0[%3, %1]
                  The operands: which array, and which item in it (row %3, column %1).
                  : memref<…>
                  The type: a 1024 × 1024 table of 32-bit floats.

                  Two ideas worth knowing

                  SSA form
                  Every value is assigned exactly once. %4 never changes after this line, so to find where any value comes from, there is exactly one line to look at. This is what makes the "which line made this?" links possible.
                  Dialects
                  The part before the dot is the dialect. arith does math, scf is loops and ifs, gpu is launches and thread ids, nvvm is NVIDIA's hardware operations. A compiler mixes dialects and moves the program from high-level ones to low-level ones.
                  Try it. Click any line in the workspace. What's this line? names each part, links every value back to the line that made it, and for loads and stores says how the GPU handles them. It is the inspector's Line tab; w opens or closes it.
                  Check yourself: in the line above, where would you look to learn what %3 is?

                  At the single line that starts with %3 =. SSA guarantees there is exactly one. In VizMLIR, click the %3 link in What's this line?.

                  Lesson 4 · Compilers

                  How a compiler builds a kernel

                  You'll learn
                  • what a compiler pass is;
                  • what "lowering" means, and the steps down to PTX;
                  • how to follow one kernel through the whole pipeline.

                  A compiler is a pipeline of small rewrites called passes. Each pass does one job, such as simplifying arithmetic or moving a kernel into its own function, and hands the result to the next. Small passes are easier to write, test, and reorder than one giant translator.

                  Lowering, step by step

                  Lowering means rewriting operations from a high-level dialect into lower-level ones, closer to the hardware. For the GPU samples in VizMLIR, the path is:

                  1. gpu.launch inside an ordinary function: the kernel's body written in place.
                  2. gpu-kernel-outlining carves the body out into a gpu.func inside a gpu.module, and replaces it with a gpu.launch_func call.
                  3. convert-gpu-to-nvvm rewrites thread ids and other GPU operations into NVIDIA's nvvm and llvm dialects.
                  4. gpu-module-to-binary turns the module into PTX, NVIDIA's GPU assembly, stored in a gpu.binary.

                  The Pass slider along the top of the workspace is this pipeline, one stop per pass. Drag it, or press [ and ], to step through it, and the inspector's Changes tab lists what each pass added, removed, or changed, with every pass listed under All passes.

                  Follow one kernel

                  Press h, or click @ symbols at the bottom, to open the inspector's Symbols tab: every function and kernel with the pass that created, changed, or lowered it. Click one to follow just that kernel like a time-lapse, all the way to its PTX.

                  Try it. In the transpose sample, press h and follow @transpose_naive_kernel from gpu-kernel-outlining to PTX. Find the line where the thread id becomes an nvvm operation.
                  Check yourself: after gpu-kernel-outlining, why does the original function still exist?

                  It runs on the CPU (the host). Outlining moves only the GPU part into its own gpu.func; the host function keeps a gpu.launch_func that starts it.

                  Timed your kernels with a profiler? In the Symbol history, Import current… puts each time next to the passes that built that kernel, and Import baseline… compares two runs. The "GPU kernels + benchmarks (mock)" sample shows this with made-up numbers.

                  Lesson 5 · Beyond GPUs

                  Scratchpads and DMA (beyond GPUs)

                  You'll learn
                  • why DSPs and NPUs use a local memory the software manages, instead of a cache;
                  • what double buffering is and why it needs two slots;
                  • how to read it in the DSP scratchpad sample.

                  A cache decides on its own what to keep close to the processor. That works well for general code, but its choices are hard to predict, and the hardware that makes them costs area and power. Many DSPs and NPUs (Hexagon's VTCM is one example) offer a scratchpad instead: a small, fast local memory that holds exactly what the program puts there. The compiler decides which tile of data lives in it, and moves the data in with DMA, a copy engine that runs beside the vector unit. Shared memory on a GPU is the same idea, managed by the threads of a block.

                  Double buffering

                  A DMA takes time. If the loop copied a tile and then computed on it, the vector unit would sit idle during every copy. Double buffering gives each tile two slots: while the loop computes on tile i in one slot, the DMA fills the other slot with tile i + 1. The first tile is loaded before the loop (the prologue), and each trip ends by swapping the roles of the slots. The price is twice the local memory per tile.

                  In MLIR, memref.dma_start starts a copy and marks a tag; memref.dma_wait on the same tag blocks until it has finished. Slots appear as a leading dimension of 2 on the buffer, and the slot of a trip is computed as (i floordiv step) mod 2.

                  Try it. Open the "DSP scratchpad" sample and step to nanodsp-promote-local. The Local memory tab shows the A and B tiles as two 64 KB slots each, filling the assumed 256 KB budget, and a schedule with the prologue loads, the prefetch of the next tile, and the waits. Click a prefetch to see its dma_start explained in the inspector, then step to nanodsp-lower-local, where each DMA has become a plain linalg.copy.

                  Limits: the view shows the order the IR expresses, not timing. Whether the copy of the next tile really hides behind the compute depends on the DMA engine, the memory bandwidth and the size of the compute, none of which are in the IR. The budget comes from nano-dsp's model of its target, not from the IR, and is labelled as assumed. After nanodsp-lower-local the copies are synchronous, so nothing overlaps at all; that form exists to run the kernel on a machine without a DMA engine.

                  Check yourself: why does the prefetch in the sample sit inside an scf.if?

                  On the last trip there is no next tile to fetch. The guard (i + step < upper bound) skips the DMA there, so it never reads past the end of the input.

                  Lab

                  Run your own compiler

                  VizMLIR reads the log mlir-opt writes when you ask it to print the code after every pass. Run your pipeline like this, then open the file with Open…: 

                  mlir-opt input.mlir -pass-pipeline='…' \
  -mlir-print-ir-before=gpu-kernel-outlining \
  -mlir-print-ir-after-all \
  -mlir-print-ir-module-scope \
  -mlir-disable-threading 2> trace.txt
                  -mlir-print-ir-after-all
                  A snapshot of the code after every pass.
                  -mlir-print-ir-before=gpu-kernel-outlining
                  One more snapshot just before kernels are carved out, so VizMLIR can tell which pass made them.
                  -mlir-print-ir-module-scope
                  The whole program in every snapshot.
                  -mlir-disable-threading
                  Keeps the log in order.

                  Add -mlir-timing to see how long each pass took (p, the inspector's Timing tab). With Watch… (Chrome and Edge), VizMLIR reloads the file each time you rerun the command, so you can keep it open beside your terminal. A failed pass is marked ✗, with the compiler's messages over the picture.

                  Reference

                  Limits of the model

                  Every model simplifies. Knowing where this one does is part of reading it well.

                  • The lanes you see are the first warp of the first block, on the first trip through any loop. When an index is a linear function of the thread ids, block ids and loop counters, the verdict is checked for every warp and every trip too, and the Checked column says so. Otherwise it reads "warp 0 only", and that one warp may not speak for the rest.
                  • They follow how NVIDIA GPUs fetch memory (32-byte sectors and 32 banks). Other GPUs work in a similar but not identical way.
                  • Index arithmetic built from values VizMLIR can't work out (data loaded from memory, for example) is reported as not analyzed rather than guessed.
                  • Reads and writes are followed through the whole pipeline: memref and affine loads and stores, then the same kernel after lowering to the LLVM dialect, where loops have become branches. Once a kernel is compiled to a binary, only its register and shared memory counts can be read.
                  • Triton GPU IR is read with its #blocked layouts. Other layouts (#mma, dot operands, shared), block pointers from tt.make_tensor_ptr, and pointers carried around a loop past its first trip are not read yet. How many programs run is set at launch, outside the IR.
                  • VizMLIR understands the most common MLIR code. If something doesn't show up the way you expect, please open an issue with the snippet.

                  Glossary

                  Bank
                  One of 32 slices of shared memory that can each serve one word per turn. Lesson 2
                  Block
                  A team of threads that can share memory. Lesson 1
                  Coalesced
                  A warp access whose addresses sit side by side, fetched in the fewest sectors. Lesson 2
                  Dialect
                  A family of MLIR operations, named before the dot. Lesson 3
                  Grid
                  All the blocks of one launch. Lesson 1
                  IR
                  Intermediate representation: the language a compiler works in between source and machine code. Lesson 3
                  Kernel
                  The part of a program that runs on the GPU, once per thread. Lesson 1
                  Launch
                  The point where the CPU starts a kernel on a grid of threads. Lesson 2
                  Lowering
                  Rewriting high-level operations into lower-level ones. Lesson 4
                  Pass
                  One step of the compiler pipeline. Lesson 4
                  PTX
                  NVIDIA's GPU assembly language. Lesson 4
                  Sector
                  The 32-byte chunk global memory is fetched in. Lesson 2
                  SIMT
                  Single instruction, multiple threads: a warp runs one instruction for all 32 threads. Lesson 1
