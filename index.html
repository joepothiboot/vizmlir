              VizMLIR / field guide

              See how your code runs on the GPU.

              When you write a program for a GPU, a compiler reshapes it in many small steps before the GPU ever sees it. VizMLIR lets you watch those steps one at a time, and draws what the result will do on the GPU: how the work is split up, where the data is kept, and whether it is read in a way the GPU is good at.

              You don't need to be a compiler expert. If you know roughly what a loop and an array are, you can follow along.

              A promise and a limit. VizMLIR only reads your code. It never runs it, and nothing leaves your browser. That also means it can't tell you exact speeds; a profiler measures those, and you can bring its numbers in here.

              Try it in a minute

              1. Open the transpose sample. Transposing a table turns its rows into columns. The sample does it three ways, and two of them contain a classic GPU mistake.
              2. The big panel in the middle is the GPU view. Scroll to Memory accesses and click a row marked in orange. It explains what is wrong and how people usually fix it.
              3. Press ] a few times to step through the compiler's work. The code on the left changes, and the picture follows.
              g swaps the GPU picture for a diagram of the code; ? lists every key.

              The GPU in four ideas

              These four ideas are all you need to read the GPU view.

              Threads
              A GPU runs the same small piece of code thousands of times at once. Each copy is a thread, and each works on its own piece of the data, like thousands of people each handed one cell of a huge spreadsheet.
              Blocks and the grid
              Threads come in teams called blocks, and all the blocks together make the grid. Teams don't wait for each other, so the GPU can spread them over its many cores however it likes.
              Warps
              Inside a block, threads move in groups of 32 called warps. Picture 32 people who must take every step together: when one reaches for memory, all 32 reach at the same moment. That is why the way neighbors read memory matters so much.
              Memory
              Global memory is the big warehouse every thread can reach, but it is far away. Shared memory is a small shelf inside each block: quick to reach, shared by that team only. Private memory belongs to a single thread.

              Reading the GPU view

              For every place your program starts work on the GPU (a launch), you'll see three things.

              • The launch. A grid of squares, one per block. The highlighted one is opened up below it so you can see its threads, 32 to a row: each row is one warp. Hover any square for its number.
              • Memory. Every array the code uses, sorted into global, shared and private, with its size and how often it is read or written.
              • Memory accesses. Every place the code reads or writes an array, with a verdict for the first warp.
              coalesced
              The 32 threads read neighboring items, like people taking books side by side from one shelf. The GPU fetches them in one trip. This is what you want.
              strided
              The threads read items far apart, like 32 people each walking to a different aisle. The GPU fetches much more than it uses and throws the rest away. The panel says how much is wasted.
              broadcast
              Every thread reads the same item. The GPU fetches it once and hands out copies, which is perfectly fine.
              bank conflict
              Shared memory has 32 counters, called banks. If several threads need different items from the same counter, they queue up. "32-way" means 32 threads waiting in one line.
              no bank conflicts
              Everyone is served at their own counter at the same time.

              Click a row to see the warp's 32 threads as colored squares (the same color means the same chunk of memory, or the same counter) and to highlight that line in the code on the left.

              Watch a kernel being built

              A kernel is the part of your program that runs on the GPU. The compiler builds it in steps called passes; the row of cards along the top shows them in order.

              • Press h, or click @ symbols at the bottom, to see every function and kernel and which step created or changed it. Click one to follow just that kernel, like a time-lapse, all the way to the GPU assembly (PTX) at the end.
              • If you have timed your kernels with a profiler, Import current… puts each time next to the steps that built that kernel. Import an older run with Import baseline… to see what got faster or slower. The "GPU kernels + benchmarks (mock)" sample shows this with made-up numbers.

              Use your own code

              VizMLIR reads the log mlir-opt writes when you ask it to print your code after every step. Run your pipeline like this, then open the file with Open…:

              mlir-opt input.mlir -pass-pipeline='…' -mlir-print-ir-before=gpu-kernel-outlining -mlir-print-ir-after-all -mlir-print-ir-module-scope -mlir-disable-threading 2> trace.txt

              What those flags ask for, in plain words:

              • -mlir-print-ir-after-all: a snapshot of the code after every step.
              • -mlir-print-ir-before=gpu-kernel-outlining: one more snapshot just before the GPU kernels are carved out, so VizMLIR can tell you which step made them.
              • -mlir-print-ir-module-scope: the whole program in every snapshot, not just the part that changed.
              • -mlir-disable-threading: keeps the log in order.

              Add -mlir-timing to see how long each step took (press p). With Watch… (Chrome and Edge), VizMLIR reloads the file every time you run the command again, so you can keep it open beside your terminal. If a step fails, its card is marked ✗ and the compiler's messages appear over the picture.

              The code diagram and what changed

              For code without GPU parts, or when you press g, the middle panel draws your code as a diagram: every operation is a box, and arrows show where each value goes next. The panel on the right lists what the current step added, removed or changed. Walk through the list with j and k; each change is highlighted in the diagram and in the code.

              Save and share

              • Your work saves itself in this browser. Close the tab and it is still there when you come back.
              • Sessions keeps named copies, and turns them into .json files you can send to someone else. Nothing is uploaded anywhere.
              • Save the diagram as a picture (PNG or SVG) from the buttons above it, and the list of changes as Markdown or JSON from the right panel. Pick changes with x and press c to copy them.

              Good to know

              • The memory verdicts look at the first warp of the first block, on the first trip through any loop. That is usually representative, but not always.
              • They follow how NVIDIA GPUs fetch memory (32-byte chunks and 32 banks). Other GPUs work in a similar but not identical way.
              • VizMLIR understands the most common MLIR code. If something doesn't show up the way you expect, please open an issue with the snippet, and we'll look at it.
